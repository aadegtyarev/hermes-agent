# Telegram-контекст (плагин `telegram-context`)

Bot API не отдаёт историю — плагин **накапливает** входящие сообщения и даёт их читать.
Доступно только то, что бот видел с момента запуска (бэкфилла старой истории нет).

## Тулы
- `telegram_recent(chat_id?, limit)` — последние сообщения чата по времени. По
  умолчанию — самый активный чат. Отсюда бери `message_id`.
- `telegram_thread(message_id, chat_id?)` — собрать тред: цепочка reply вверх до
  корня + все ответы ниже, хронологически, кто→кому.
- `telegram_search(query, chat_id?)` — полнотекстовый поиск по накопленному (см. ниже).
- `telegram_dm_allowlist()` — кто попал в DM-allowlist (собран из work-чатов).

### Как работает `telegram_search`

Полнотекстовый индекс (SQLite FTS5), не поиск подстроки:
- **Регистр не важен**, включая кириллицу («Прошивка» / «ПРОШИВКА» / «прошивка» —
  без разницы; это специально чинили, обычный SQL так не умеет для кириллицы).
- **Каждое слово запроса ищется как начало слова (префикс), не точная форма.**
  Запрос `query="прошив"` найдёт «прошивка», «прошивку», «прошивки» — все
  падежи/формы разом. Поэтому **лучше искать короткий стем/корень слова**, а
  не гадать точную грамматическую форму, которую использовали в чате: `"контроллер"`
  надёжнее, чем `"контроллеров"` (последнее найдёт только слова, начинающиеся
  ИМЕННО с "контроллеров" — не более короткую форму).
- Несколько слов в запросе — ищутся через И (все слова должны быть в сообщении,
  необязательно подряд): `query="прошивка контроллера"` требует оба слова.
- Составные токены типа `wb-map12` / `v2.42` при индексации бьются на части
  (`wb`, `map12` / `v2`, `42`) — искать можно по любой из частей.
- История, накопленная ДО обновления поиска, тоже проиндексирована — доступна
  вся, не только новые сообщения.

### Отчёт/дайджест за период
И `telegram_recent`, и `telegram_search` дополнительно принимают:
- `since_hours_ago` / `until_hours_ago` — окно по времени (часы назад, не сырые
  таймстампы — «за последнюю неделю» = `since_hours_ago=168`).
- `count_only: true` — сначала узнать объём (кол-во сообщений, диапазон дат,
  примерный размер), без самого текста — прежде чем листать большое окно.
- `cursor` — постраничный обход: `cursor=0` начинает с самого старого
  сообщения в окне, дальше бери `next_cursor` из ответа, пока `has_more: true`.
  Без `cursor` — обычное поведение «последние N», как раньше.

Порядок для отчёта за большой период (неделя+): `count_only` → если объём
большой, слистывать через `cursor` пачками, не пытаясь утянуть всё разом в
контекст.

## Как устроен гейтинг (не тул, а поведение)
- **work-чаты** (`TELEGRAM_WORK_CHATS`): бот отвечает; кто там пишет — автоматически
  получает право писать боту в личку.
- **read-only чат** (`TELEGRAM_READONLY_CHATS` / `/hermes_readonly`): бот читает
  для контекста, но **не отвечает** — гарантия жёсткая: даже прямое обращение
  к боту в этом чате не получит ответа, блок стоит и на уровне диспетчеризации,
  и на уровне самой отправки в Telegram API. Участники DM-доступ НЕ получают.
- **личка**: бот отвечает только тем, кто в allowlist (участник work-чата,
  проверяется по членству, + `TELEGRAM_DM_EXTRA_USERS`).
- Добавили бота в чужой чат — он его **игнорирует**.
- **client-чат** (`/hermes_program`) — изолированный чат с посторонним
  (партнёром, клиентом и т.д.), см. отдельный раздел ниже.

## Client-чаты: изолированный чат с посторонним

Универсальный механизм для «один на один чатик с внешним человеком, и таких
сотни» — партнёры журналиста, клиенты техподдержки и т.д. Регистрируется
командой `/hermes_program`:
- `/hermes_program <имя>` в чате команды (только если имя новое и вызывающий —
  глобальный admin) — создаёт программу, этот чат становится её «чатом команды».
- `/hermes_program [имя]` в новом чате с посторонним — регистрирует ТЕКУЩИЙ чат
  как client-чат под этой программой. Доступно любому живому участнику чата
  программы (не обязательно глобальному admin). Имя можно не указывать, если
  вызывающий состоит ровно в одной программе.

### Как себя вести в client-чате
- Ты — полноценный ассистент, а не пересылатель сообщений. Реально старайся
  помочь: отвечай по существу, используй `gdoc_read`/`gdoc_comments` для
  документов, которые прислали в этом же чате.
- Источники — ссылками. Если что-то не сказано прямо, а это твой логический
  вывод — явно помечай как предположение, не выдавай за факт.
- Зови команду через `escalate_to_team(message)`, когда реально не уверен в
  ответе, или собеседник прямо просит позвать кого-то более опытного. Это
  **нормальное профессиональное действие** — как стажёр зовёт старшего
  напарника, а не провал. Не стесняйся звать, даже если до этого уже
  пробовал помочь сам.
- `escalate_to_team` сам резолвит, в какой чат команды слать — chat_id
  передавать не нужно и нельзя (инструмент не примет чужой чат). Есть
  кулдаун на чат — повторный вызов слишком быстро просто не отправится
  повторно, в ответе будет `retry_after_seconds`; в этом случае продолжай
  помогать разговором, не дёргай инструмент снова.

### Изоляция client-чата (жёсткая, не обходится)
Сессия в client-чате видит **только свою собственную историю** — это
специально, не баг:
- `telegram_search`/`telegram_recent` — без `chat_id` или с чужим chat_id
  будут заблокированы; передавай `chat_id` этого же чата явно.
- `session_search`, `gdrive_search` — недоступны вообще в client-чате.
- `gdoc_read`/`gdoc_comments` — работают только с документом, ссылка на
  который уже была в этом же чате (кто-то прислал её сюда). Другой документ
  открыть нельзя, даже если знаешь его ссылку.
- `send_message` — только в этот же чат. Единственный способ достучаться до
  команды снаружи — `escalate_to_team`.

Рабочие/read-only чаты этим НЕ ограничены — видят всё как раньше, в том
числе историю client-чатов (это тоже специально: команда должна мочь
посмотреть, что писал конкретный партнёр, из своего рабочего чата).

Если партнёр долго ничего не пишет боту напрямую (без упоминания) — это не
значит, что его сообщения потеряны: отдельная фоновая проверка (не тул,
работает сама) время от времени просматривает такие чаты и при необходимости
тоже зовёт команду — про неё ничего специально делать не нужно.

## Паттерн для разбора
1. Пришёл вопрос/жалоба в чате → `telegram_thread(message_id)` собрать весь тред,
   понять кто что сказал и хронологию.
2. Нужен более широкий контекст → `telegram_recent` / `telegram_search`.
3. Дальше — обычный разбор (ssh на контроллер, поиск по коду/форуму и т.д.).
